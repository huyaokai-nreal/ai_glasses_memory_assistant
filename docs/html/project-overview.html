1. 这套系统解决什么问题

专业解释

这个项目不是普通聊天机器人，而是在验证一个个人长期记忆 agent 的核心管道： 多输入来源先标准化，再进入候选抽取、敏感门控、去重/更新、结构化保存、证据追溯、按需召回和回答生成。

代码上，主锚点是 GlassesChatService.chat()。 它把 planner/router、memory store、timeline store、文档召回、后台 job、debug 和 audit 串成一个 turn。

通俗理解

可以把它想成一个“会记事但不乱记事的个人助理”： 你说过的原话先进账本；真正长期有价值的信息再整理成便签；回答时只拿当前问题需要的几张便签和原话证据出来。

它不追求把所有聊天都塞进模型，而是追求：以后问“我最近在忙什么”“我之前原话怎么说”“我接下来有什么安排”时，有证据地回答。

当前真实定位 已有 Web/语音 demo、SQLite 记忆库、raw timeline、文档归档、连续输入验证、后台 memory job、debug/audit/tests/evals。 但它还不是生产级 AI 眼镜助手：没有真实硬件 runtime、原生 App、音频上传/ASR、主动提醒推送或可靠任务队列。

2. 产品全景：眼镜、App、Web demo 和后端各自做什么

眼镜端：低摩擦输入

最终形态里，眼镜负责随手语音、环境片段和即时反馈。当前只用浏览器语音作为早期交互替身。

手机 App：管理和补充

最终形态里，App 负责文档上传、音频输入、手动文本补充、记忆管理和结果查看。当前只有后端雏形。

Web demo：验证体验

当前 Web UI 用来验证聊天、语音按钮、TTS、定位、当前记忆面板、Debug 抽屉和 memory job 轮询。

后端管道：统一内化

无论来自聊天、导入、文档还是连续输入，都应该进入同一套候选、门控、去重、写库和 audit。

记忆库：长期事实

EventMemoryStore 保存 profile、event、task、decision、preference、observation 和文档 metadata。

原文库：证据账本

TimelineStore 保存 raw turn 和 chunk，用于原话回忆、证据追溯和全文搜索。

这个分工来自当前 docs/context/demo-features.md 和 docs/context/current-status-and-gaps.md： 页面只写当前能验证的能力，未来硬件/App 能力统一标为边界或后续方向。

3. 一次对话怎么走

当前最重要的主链路是 /api/chat。不要把它理解成“收到消息后直接问大模型”。 真实路径会先写原话、做 planner/router 判断、按需召回，再决定本地回复还是调用主模型，最后处理记忆写入和 audit。

1. HTTP 输入 message、user_id、session_id、位置和是否延迟写记忆。
2. 写 timeline TimelineStore.add_turn() 先保存用户原话 chunk，作为后续证据。
3. planner/router turn_planner.py 决定 fast path、召回需求、位置/web/文档等分支。
4. 准备上下文 按需召回 profile、event、timeline、document、location 或 web。
5. 生成回复 简单场景本地回复，复杂场景进入 AIAgent.run_conversation()。
6. 写入和审计 候选过门控后同步保存或进入后台 job，并写入 chat_audit.jsonl。
为什么要这样拆？

工程原因

这样可以把“是否需要记忆”“是否需要召回”“是否需要主模型回答”“是否需要后台写入”拆成可观测决策。 出错时可以从 debug 和 audit 定位是哪一步偏了，而不是只看到一个最终回答。

白话例子

用户说“你好”，系统不需要查记忆也不需要写记忆；用户说“我喜欢安静靠窗”，系统要保存偏好； 用户问“我之前原话怎么说”，系统要查 timeline，而不是让大模型凭印象编。

4. 记忆系统四层

当前 Memory Kernel 是轻量 contract，不是新数据库，也不是向量库。它的作用是把长期记忆分层，并统一 source_trace 和 recall_trace，让“这条记忆从哪里来、这次回答用了什么证据”可解释。

raw_timeline

专业解释：保存聊天原话、capture chunk 和可搜索证据，服务原文回忆和 evidence 追溯。

通俗理解：像“原话账本”。你当时怎么说，它尽量按 chunk 留底。

structured_memory

专业解释：保存 profile、event、task、decision、assistant_preference、document metadata 等结构化长期记忆。

通俗理解：像“整理后的便签”。不是所有原话都进便签，只保存长期有价值的信息。

reflection

专业解释：后台 observation，把多条 source memory 归纳成近期状态、项目主线或工程偏好。

通俗理解：像“阶段性总结”。不是一句原话，而是多条证据合起来的判断。

runtime_recall

专业解释：当前 turn 临时注入的少量 top-k 上下文，只服务本轮回复。

通俗理解：像“答题时拿出来的几张卡片”。答完不会自动变成新记忆。

几个容易混淆的概念

概念 专业解释 白话说明
timeline 原文时间线，支持 raw chunk 搜索和 evidence ids。 原话账本，回答“我之前怎么说的”。
structured_memory 可展示、可搜索、可召回的长期结构化事实。 整理后的便签，回答“我喜欢什么、我有什么安排”。
observation 后台从多条 source memory 归纳出的长期观察。 阶段性总结，回答“我最近主要在忙什么”。
confidence_policy 集中解释置信度阈值、是否通过和低置信度处理。 刹车规则：不确定时宁可新增或忽略，也不误合并、误替换。
evidence_ids 结构化记忆指向 raw chunk 的证据引用。 便签背后的原始凭据，方便追问“你凭什么这么记”。

5. 输入来源：不同入口，同一套门控

最终产品会有眼镜语音、App 文档、App 音频和手动文本等入口。当前原则是： 入口可以不同，但长期记忆写入不能各写各的，更不能绕过敏感门控。 

聊天 / 手动新增 / 文本导入 / JSON 导入 / Markdown 上传 / continuous_capture
-> 标准化输入
-> raw timeline/chunk 记录原文证据
-> MemoryWriteCandidate
-> should_write_memory_candidate()
-> 去重或合并证据
-> EventMemoryStore.add_memory()
-> debug/audit
输入来源 当前处理方式 学习时要记住的边界
/api/chat planner 生成候选，按需召回，回复后同步或后台写记忆。 普通聊天不应默认读写个人记忆。
/api/memory/import 文本/JSON 标准化后生成候选，再过门控和去重。 confirm=true 也不能绕过敏感信息规则。
Markdown 上传 完整原文进入 documents，后续问细节时召回原文或片段。 不把每一行静默拆成 event memory。
continuous_capture append 写 timeline chunk，stop 合并文本后进入 import 和记忆候选流程。 它是长输入验证，不是硬件 ASR runtime。
未来 App 音频 应先 ASR 转写，再按文本或 capture 进入统一管道。 当前没有音频上传、原始音频保存或 ASR 管道。
核心原则 新入口可以扩展，但不能直接写 SQLite。长期记忆必须经过 should_write_memory_candidate()， 并能在 debug/audit 中解释为什么保存、拒绝、合并或等待确认。

6. 关键机制例子

偏好怎么保存

用户说“我喜欢安静靠窗的位置”。planner 生成 profile 候选，门控通过后保存为 kind=profile、memory_type=preference。后续问订座偏好时召回。

任务怎么保存

用户说“明天下午 3 点和 Alex 开周会”。系统解析时间，生成 event/task 候选，保存后能回答“我接下来有什么安排”。

原话为什么查 timeline

用户问“我之前原话怎么说”。这不是总结问题，而是 raw evidence 问题，应查 TimelineStore.search_chunks()，不能只看结构化摘要。

文档为什么不拆成一堆记忆

Markdown 上传先保存完整 documents.content。用户问文档细节时读原文，避免只靠 summary 丢细节。

项目状态变化例子：

早期记忆里有“项目主线是南太行”。后来用户明确说“现在主线是 AI 眼镜长期记忆机制”。

正确行为不是让旧 source 永远污染回答，而是通过新的 project_state 和 observation/source evidence 更新近期状态。 后续问“我最近在忙什么？”应该优先回答 AI 眼镜长期记忆机制，而不是继续说南太行。

低置信度 fallback 例子：

dedupe classifier 如果说“可能重复”但 confidence 很低，系统应该 fallback_to_new，保存成新记忆，而不是误合并。

observation update 如果低置信度返回 supersede，也应回退为 new，避免把旧 observation 错误替换。

7. 可观测与测试：出了问题先看哪里

这套项目很重视“为什么这样答”和“为什么这样记”。可观测性不是附加功能，而是判断记忆系统是否可靠的核心。

工具/输出 回答的问题 典型用途
前端 Debug 本轮 planner、router、召回、写入、web/location、耗时大概是什么。 快速判断“为什么没查记忆”“为什么调了 LLM”。
chat_audit.jsonl 每轮输入、回复、召回、写入、debug 和耗时的长期诊断记录。 排查答错、答慢、没记住、乱记住。
/api/memory/jobs 后台写入 job 是 pending、running、saved、rejected、skipped 还是 failed。 解释“回复已经返回了，记忆后来有没有写成功”。
eval report 场景门禁是否通过，active 和 target 缺口分别是什么。 避免只靠手工对话判断系统没问题。

当前核心验证命令

conda run -n hermes python -m unittest ai_glasses_memory_assistant.tests.test_agent_bridge_policy -q
conda run -n hermes python -m unittest ai_glasses_memory_assistant.tests.test_evals_metrics -q
conda run -n hermes python -m unittest discover ai_glasses_memory_assistant/tests -q
conda run -n hermes python -m ai_glasses_memory_assistant.evals.runner --mode live --repeat 1 --category memory_mechanism --strict --background-wait 15
怎么读 active / target eval active eval 是当前门禁，失败就说明当前承诺能力有问题；target eval 是已知缺口，用来暴露后续方向，不应该靠硬编码强行通过。

8. 当前已完成 vs 不能误判完成

已完成：Web/语音 demo 入口

可以验证文本聊天、浏览器语音、TTS、定位、当前记忆面板和 Debug 抽屉。

已完成：SQLite 记忆与 timeline

events.db 保存结构化记忆和文档，timeline.db 保存 raw turn、chunk、capture 和 job 公开状态。

已完成：记忆门控和 confidence policy

写入、dedupe、correction、observation update 的低置信度路径都有 debug/audit 解释。

已完成：复杂 observation/source evidence eval

已有 active 机制 eval 覆盖项目状态回顾、source evidence 和低置信度 fallback。

未完成：真实眼镜硬件 runtime

当前浏览器语音只是交互替身，没有蓝牙、摄像头、传感器或硬件常驻采集。

未完成：原生手机 App 和音频管道

已有文档/文本后端雏形，但没有原生 App、音频上传、ASR 转写或原始音频管理。

未完成：主动提醒 runtime

/api/reminders/check 是手动检查，不是后台主动推送。后续还需要授权、触发窗口和抑制策略。

未完成：可靠 worker 队列

memory job/capture 公开状态可从 SQLite 恢复查询，但没有任务重放、超时补偿、跨进程调度。

接下来更值得做什么

任务完成/取消与项目 scope

继续补底层记忆机制时，优先解决 task 生命周期、项目边界和过期状态，而不是重复做已覆盖的 fallback。

长上下文 source 组合

验证多段输入、多条 source evidence 如何支持更稳定的项目回顾和长期 observation。

主动提醒 eval 对齐

产品能力方向上，先让 eval 调真实 check_reminders()，再设计后台定时器。

核心代码入口速查

这不是完整文件清单，只列理解系统时最有帮助的锚点。

锚点 负责什么 为什么重要
GlassesChatService.chat() 主聊天 service，串起 planner、召回、回复、写入、audit。 理解一次对话必须从这里开始。
turn_planner.py 决定 fast path、是否召回、是否写记忆、是否进入 continuous capture。 它决定“这句话属于什么场景”。
intent_policy.py 长期记忆写入门控，拒绝低价值、敏感或不确定候选。 它是“不乱记”的核心。
EventMemoryStore 结构化记忆和 documents 的 SQLite 存储。 它保存整理后的长期便签。
TimelineStore raw turn、chunk、capture、memory_jobs 和全文搜索。 它保存原话证据和后台 job 公开状态。
evals/runner.py 离线 live eval runner，跑真实 service.chat 场景。 它把“能不能工作”变成可重复门禁。
