# AI 眼镜 Demo 近期产品备忘

更新时间：2026-05-14。本文记录近期产品讨论和周会准备事项，供后续 Codex 接手、产品梳理和 demo 汇报使用。

## 1. Codex 技能自动触发

目标问题：Codex 是否能根据用户自然语言 prompt 自动判断需要哪些技能，而不是每次都依赖用户提醒。

期望方向：

- 当 prompt 明显需要某类能力时，Codex 应自动调用已安装技能。
- 当缺少合适技能时，Codex 应主动提醒用户“可以安装某个技能”，并说明为什么需要。
- 技能触发应该基于任务语义，而不是要求用户记住技能名称。

产品价值：降低用户使用门槛，让用户只表达自然需求，不需要理解底层技能系统。

## 2. 网页链接、录音等输入

当前 demo 已经验证的输入形态：

- Web 文字聊天。
- 浏览器语音输入，用来模拟眼镜语音入口。
- Markdown 文档和普通文本导入。
- `continuous_capture` API，用来验证长输入或语音转写文本如何进入统一管道。

需要继续确认的输入形态：

- 网页链接：用户给一个 URL 后，系统是否抓取、摘要、归档，并在后续问答或周报里召回。
- 录音文件：手机 App 或网页上传录音后，是否先转写，再进入文本导入、候选抽取、敏感门控和 evidence 追溯。

边界：当前 demo 没有生产级音频上传、ASR 转写和原始音频管理。未来做录音入口时，不应绕过现有记忆门控。

## 3. 记忆面板不应要求用户频繁 review

产品判断：用户大概率不想长期管理“我的记忆”，因为人工 review 记忆面板很耗精力。

记忆面板的定位应更轻：

- 默认只做展示和解释，让用户知道系统记住了什么。
- 不要求用户频繁逐条审核。
- 用户发现错误时，可以低成本纠正、删除或追溯来源。

替代方案：

- 自动抽取：系统从聊天、文档、转写文本里抽取有长期价值的信息。
- 敏感门控：密码、token、证件号等敏感内容不能静默长期保存。
- 低打扰确认：只有高风险或低置信度内容才需要用户确认。
- 可追溯证据：关键记忆需要关联原文 chunk 或文档来源。
- 可纠错删除：用户能删除或纠正错误记忆，后续召回不再沿用旧事实。

## 4. 真人测试和手机 App 时机

近期测试路径：

1. 功能基本完善后，用手机登录本地 demo 做真人实时语音测试。
2. 手机和 Mac 必须在同一局域网，必要时使用 HTTPS 才能稳定测试语音和定位。
3. 真人测试基本 OK 后，再考虑写成手机 App。

当前限制：

- 同网测试仍依赖 Mac 上的本地服务。
- 浏览器语音受权限、HTTPS、安全上下文和网络环境影响。
- 原生 App 可以脱离 Mac，但需要等核心记忆、输入、召回和周报链路先验证清楚。

## 5. 周会汇报材料

今天下午周会需要给领导汇报这个 demo。汇报材料应先打磨文案，再生成单独 HTML。

汇报要求：

- 介绍 demo 能做什么。
- 解释背后逻辑，但要通俗易懂。
- 表现形式简洁，适合会议中快速讲清楚。
- 明确当前边界，不把计划中的能力说成已经完成。
- 可以邀请朝阳、劲阳一起参加讨论，重点讨论产品方向和下一步验证。

建议汇报主线：

```text
用户自然输入
-> 系统判断意图
-> 按需读取记忆、原文、位置、网页信息
-> 先回答用户
-> 后台沉淀长期有用的记忆
-> 后续用于回忆、总结、提醒和周报
```

## 6. 最近 5 天日报导入和周报 POC

目标：把最近 5 天的日报 Markdown 都导入 demo，验证它是否能帮助用户写周报。

本轮先留占位，不定位实际文件路径。等日报文件路径确认后，再执行导入验证。

建议 POC 步骤：

1. 收集最近 5 天日报 Markdown 文件。
2. 通过现有 Markdown 文档导入或 `/api/memory/import` 导入 demo。
3. 调用 `/api/weekly-report` 生成周报草稿。
4. 检查周报是否能按项目、完成事项、决策、风险、下一步组织内容。
5. 对照原始日报检查证据是否可追溯，避免生成没有来源的总结。

验收标准：

- 能基于 5 天日报生成可用周报草稿。
- 周报内容能覆盖主要项目和进展。
- 重要结论能回到原始日报或文档片段。
- 不要求用户手动整理每条记忆。
- 如果效果不足，应记录是导入、抽取、召回、分组还是生成阶段的问题。
